# ClinGen ClinVar Annotation Submission File Specification

This document describes the structure and meaning of the ClinVar annotation submission file generated by the ClinGen ClinVar Curation (CvC) review and submission process.

## File Overview

| Property | Detail |
|---|---|
| **Format** | Newline-delimited JSON (one JSON object per line) |
| **Naming Convention** | `clinvar-annotation-submission-{batch_id}-{YYYYMMDD}.json` |
| **Location** | [Clinvar Submissions](https://drive.google.com/drive/folders/1w_hncksAMGAmVIVVDJVD3M0fGVj4KL80) shared Google Drive folder |
| **Source** | BigQuery table `clinvar_curator.cvc_annotations` filtered to annotations assigned to the batch |

Each line in the file is a self-contained JSON object representing one annotation record. There is no wrapping array or outer structure.

**Important:** ClinVar has requested that submission files separate `flagging candidate` records from `remove flagged submission` records. When a file contains only `remove flagged submission` requests, ClinVar should be notified that the file is strictly for flag-removal purposes.

### Example

```json
{
  "Variation ID": "12345",
  "VCV": "VCV000012345",
  "SCV ID": "SCV000067890.3",
  "Submitter ID": "505878",
  "Action": "flagging candidate",
  "Reason": "Classification not supported by evidence",
  "Notes": "See detailed rationale",
  "Timestamp": "2026-05-10T14:30:45Z",
  "Date Created": "2026-04-01",
  "ClinVar Release Date": "2026-03-15",
  "Is Annotation Outdated": false,
  "Is Annotated SCV Deleted": false,
  "SCV Deleted Release Date": null
}
```

## Column Definitions

Each JSON object contains the following 13 fields, listed in order of appearance.

### Identification Fields

| # | Field | Type | Description |
|---|---|---|---|
| 1 | **Variation ID** | String | The ClinVar Variation ID that uniquely identifies the variant being annotated. |
| 2 | **VCV** | String | The ClinVar VCV accession (e.g., `VCV000012345`). This is the top-level variation record in ClinVar that aggregates all submissions for a given variant. |
| 3 | **SCV ID** | String | The ClinVar SCV accession with version number, formatted as `{scv_id}.{scv_ver}` (e.g., `SCV000067890.3`). This identifies the specific submission (and version) being annotated. |
| 4 | **Submitter ID** | String | The ClinVar-assigned numeric identifier for the organization that submitted the SCV record. |

### Annotation Fields

| # | Field | Type | Description |
|---|---|---|---|
| 5 | **Action** | String | The annotation action determined by the curator. One of three values: |
| | | | **`flagging candidate`** -- The SCV submission has been identified as a candidate for flagging due to concerns with the submitted classification. |
| | | | **`remove flagged submission`** -- A previously flagged SCV should have its flag removed (e.g., the submitter has corrected the issue). |
| | | | **`no change`** -- The SCV was reviewed and no action is warranted at this time. Records with this action are auto-approved during review and are **not included** in the submission file under normal workflow (they are filtered out during batch assignment). |
| 6 | **Reason** | String | The curator's rationale for the chosen action. The available reasons depend on the action (see [Reason Values by Action](#reason-values-by-action) below). |
| 7 | **Notes** | String | Additional context or commentary from the curator. Newline characters in the original notes are replaced with spaces in the output. Notes are generally encouraged when the Reason is "Other" (see [Reason Values by Action](#reason-values-by-action)). **Caution:** Notes for flagged submissions are displayed in the ClinVar UI -- do not include internal or non-public information. |

### Temporal Fields

| # | Field | Type | Description |
|---|---|---|---|
| 8 | **Timestamp** | String | The date and time when the annotation was created, in ISO 8601 format with UTC timezone (e.g., `2026-05-10T14:30:45Z`). |
| 9 | **Date Created** | String | The date the annotation record was initially created in the curation system, in `YYYY-MM-DD` format (e.g., `2026-04-01`). This is the "as of" date for the annotation. |
| 10 | **ClinVar Release Date** | String | The ClinVar release date associated with this annotation. Indicates which ClinVar data release the annotation was based on. |

### Status Fields (ClinGen Internal Use)

The status fields are included for the benefit of ClinGen curators and reviewers. They are **not intended for use by the consuming ClinVar process** but provide useful context about the state of the annotated SCV at the time of submission.

| # | Field | Type | Description |
|---|---|---|---|
| 11 | **Is Annotation Outdated** | Boolean | `true` if the SCV has been updated in a ClinVar release newer than the one the annotation was based on, meaning the annotation may no longer reflect the current state of the submission. `false` otherwise. |
| 12 | **Is Annotated SCV Deleted** | Boolean | `true` if the SCV that was annotated has been deleted from ClinVar (the submitter withdrew or removed their submission). `false` otherwise. |
| 13 | **SCV Deleted Release Date** | String or null | The ClinVar release date on which the SCV was deleted. `null` if the SCV has not been deleted. |

## Reason Values by Action

The available Reason values depend on the Action. The following lists apply to **Sequence Variant (non-CNV)** submissions. When the selected Reason is "Other," a descriptive Note is generally encouraged to provide context (see the Notes field in [Annotation Fields](#annotation-fields)).

### Flagging Candidate Reasons

Organized by category:

#### Submission Errors

- New submission from submitter that appears to have been intended to update this older submission
- Other submission error

#### Unnecessary Conflicting or Case-level Interpretation Submissions

- Clinical significance appears to be a case-level interpretation inconsistent with variant classification
- Unnecessary conflicting claim for distinct condition when other classifications are more relevant

#### Old/Outlier/Unsupported Submissions

- Older and outlier claim with insufficient supporting evidence
- Older claim that does not account for recent evidence
- Claim with insufficient supporting evidence
- Outlier claim with insufficient supporting evidence
- Conflicts with expert reviewed submission without evidence to support different classification
- P/LP classification for a variant in a gene with insufficient evidence for a gene-disease relationship

#### Miscellaneous

- This phenotype is not a monogenic disease. The terms P/LP are not appropriate.
- Other

### Remove Flagged Submission Reasons

- Other SCVs submitted for VCV record
- Gene-disease relationship classification has changed
- Discussion with submitter
- Curation error
- Other

## Row-Level Semantics

Each row (JSON line) in the file represents **one reviewed and approved annotation** of a ClinVar submission (SCV). Only the most recent annotation for a given SCV is included at the time the file is generated.

A submission file for a given batch contains only annotations that:

1. Have been **reviewed** by an authorized reviewer with a status of "OK".
2. Have an **action** of either `flagging candidate` or `remove flagged submission` (annotations with `no change` are excluded).
3. Have been **assigned** to the batch identified in the filename.

A single batch may contain annotations across multiple VCV/SCV records and multiple submitters.

## Terminology Notes

### Submission

The term **submission** refers both to the file or batch being sent and to each individual record within it. This dual usage is consistent with how ClinVar, GenCC, and other submission-based processes use the term in their documentation and discussions -- for standard ClinVar submissions from submitters and for CvCuration submissions from ClinGen alike. When reading this document or related communications, use context to determine whether "submission" means the file/batch or an individual record.

### Annotation

The term **annotation** (or **annotation record**) refers to any record captured by ClinGen curators as they assess ClinVar SCVs. Annotations can have an action of `no change`, `flagging candidate`, or `remove flagged submission`. When an annotation is reviewed, approved, and assigned to a batch, it becomes a submission record in the generated submission file.

## Batch Lifecycle

1. **Curation** -- Curators create annotations in the ClinGen ClinVar curation system against specific SCV records.
2. **Review** -- Annotations are loaded into the Review & Submit Google Sheet, where reviewers examine each annotation and mark it as OK, Fixed, Archive, or Question.
3. **Assignment** -- Approved annotations (status = OK, action = flagging candidate or remove flagged submission) are assigned to the next batch.
4. **Generation** -- The submission file is generated from all annotations assigned to the batch.
5. **Finalization** -- The batch is finalized, a draft email is created with the file attached, and the system prepares for the next batch cycle.
6. **Reconciliation** -- After ClinVar processes the submission file, any failed submission requests are assessed. Failed requests may require re-review by curators, or in cases where the submitter updated the SCV without substantive changes, may be automatically reflagged.

## Frequently Asked Questions

These questions were originally raised in the context of extending this file format to CNV variations. The answers apply generally to any implementation that produces a submission file conforming to this specification.

### What does "Date Created" refer to?

The date the annotation record was created in the curation system -- i.e., when the curator assessed the SCV and recorded their finding. It does not refer to when the SCV itself was created in ClinVar. See field #9 in [Temporal Fields](#temporal-fields). This field is not known to be critical to ClinVar's processing, but generators should provide a valid date string for consistency.

### What does "Timestamp" refer to, and how does it differ from "Date Created"?

Timestamp (field #8) is the datetime-precision equivalent of Date Created (field #9) -- both refer to when the curator created the annotation. Timestamp includes the time component in ISO 8601 UTC format (e.g., `2026-05-10T14:30:45Z`), while Date Created is date-only. See [Temporal Fields](#temporal-fields). Neither is known to be critical to ClinVar's processing, but both should be populated with valid, consistent values.

### What does "ClinVar Release Date" refer to? Is it always the latest release?

It is the ClinVar release that was current when the curator created the annotation -- not necessarily the latest release at the time the submission file is generated. If a newer release has been published since, the annotation may be marked as outdated (see [Is Annotation Outdated](#status-fields-clingen-internal-use)). See field #10 in [Temporal Fields](#temporal-fields). This field is not known to be critical to ClinVar's processing, but generators should provide the accurate release date the annotation was based on.

### Why are both Variation ID and VCV included?

Both were included for convenience. Variation ID (field #1) is the internal numeric identifier, useful in auditing and computational processing from the producer's vantage point. VCV (field #2) is the user-facing accession string (e.g., `VCV000012345`) that most submitters and ClinVar users are comfortable working with. There is no known technical requirement from ClinVar's side to include both, but both are populated for completeness -- defer to ClinVar if one or the other can be left blank. See [Identification Fields](#identification-fields).

### What does "Is Annotation Outdated" mean?

An annotation is outdated when the SCV it was based on has been updated in a ClinVar release newer than the one used during curation (see field #11 in [Status Fields](#status-fields-clingen-internal-use)). This means the curator's assessment may no longer reflect the current state of the submission. As noted in that section, all status fields are for ClinGen internal use and are not intended for ClinVar's processing, but generators should populate them with correct Boolean values.

### What does "SCV Deleted Release Date" mean?

The ClinVar release date on which the annotated SCV was removed from ClinVar by its submitter. This is `null` if the SCV has not been deleted. See field #13 in [Status Fields](#status-fields-clingen-internal-use). Like other status fields, this is for ClinGen internal use. Generators should provide a valid date string or `null`.

### Why would a deleted SCV appear in the file?

It generally would not. If an SCV is deleted after an annotation is created but before the batch is finalized, the annotation is flagged during review via the "Is Annotated SCV Deleted" field (see [Status Fields](#status-fields-clingen-internal-use)) and typically assigned an "Archive" review status rather than being included in the submission. The status fields are carried through to provide full context when reviewing edge cases.

### What are the possible values of "Action"?

See field #5 in [Annotation Fields](#annotation-fields). The two actionable values are `flagging candidate` and `remove flagged submission`. A third value, `no change`, exists in the curation system but is excluded from submission files during batch assignment (see [Row-Level Semantics](#row-level-semantics)). The Action field is critical to ClinVar's processing -- it determines what ClinVar does with the record. Also note that ClinVar has requested these two action types be submitted in separate files (see [File Overview](#file-overview)).

### What Reason values are valid for each Action?

The available reasons depend on the action. The current Sequence Variant (non-CNV) reason values are listed in [Reason Values by Action](#reason-values-by-action). The Reason field is critical to ClinVar's processing. Generators for other variant types (e.g., CNV) should establish an appropriate set of reason values and document them alongside the existing lists.

### Should the file identify which group created the submission?

The current schema does not include a field identifying the submitting organization (e.g., ClinGen). As additional groups begin producing these files, adding such a field may be appropriate. This is an open topic for discussion with ClinVar.
